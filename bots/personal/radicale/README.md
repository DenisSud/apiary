# Radicale on the RPi (cal.sudakov.site)

The server side of the personal calendar: Radicale 3.8.0 in a rootless podman
container on the RPi (`denis@192.168.1.6`), behind the existing Caddy.

## Layout on the RPi

```
~/radicale/
├── compose.yml          # from this directory
├── config/
│   ├── config           # Radicale config (from here)
│   ├── users            # htpasswd, generated by deploy.mjs (never committed)
│   └── rights           # from here
└── data/collections/    # the calendars themselves (owned by denis)
```

## Deploy / update

```bash
node deploy.mjs                    # idempotent: config, users, container, Caddy, verification
RPI_HOST=pi.wan node deploy.mjs    # from outside the LAN
```

What it does: resolves `radicale-denis` + `radicale-agent` from Bitwarden,
hashes them into `config/users` (sha512 crypt via `openssl passwd -6 -stdin`,
so no secret touches argv), copies the config, recreates the container, adds
the `cal.sudakov.site` vhost to `/etc/caddy/Caddyfile` if missing, creates
`/denis/main/` and verifies that the agent can read that calendar and *cannot*
see `/denis/`.

## Operations

```bash
ssh 192.168.1.6 'cd ~/radicale && podman-compose --in-pod false up -d --force-recreate'
ssh 192.168.1.6 'podman logs --tail 50 radicale'
ssh 192.168.1.6 'podman exec -it radicale /venv/bin/python -c "import radicale; print(radicale.VERSION)"'

# backup (plain tar: keep-id keeps the data owned by denis, no subuid surprises)
ssh 192.168.1.6 'tar czf ~/radicale-$(date +%F).tar.gz -C ~/radicale data'

# restore
ssh 192.168.1.6 'cd ~/radicale && podman-compose --in-pod false down && tar xzf ~/radicale-<date>.tar.gz && podman-compose --in-pod false up -d'
```

## Decisions and gotchas

- **`podman-compose --in-pod false`** is required: `userns_mode: keep-id`
  cannot be combined with a pod, and keep-id is what makes `data/` owned by
  `denis` on the host (otherwise it belongs to a subuid and host-side backups
  need root or container-side tar).
- **`restart: always`**, not `unless-stopped`: this RPi's
  `podman-restart.service` only resurrects `restart-policy=always` containers
  at boot.
- **Permissions are case-sensitive** in Radicale's rights file: lowercase
  `rw` covers the *items* in a collection (events), uppercase `RW` covers the
  collection itself. MKCALENDAR checks lowercase `w` on the new path, so a
  calendar that should be usable needs `rw`.
- **`--force-recreate`** on redeploy: Radicale reads `config` and `rights` once
  at startup, so a plain `up -d` would keep running with the old files.
- Timed events are stored in UTC and all-day events as dates, so no VTIMEZONE
  is needed and every client renders them in its own zone.
- No VALARM and no ATTENDEE: this is a single-user calendar. Adding reminders
  means adding a VALARM component in `extensions/calendar/ics.ts` and letting
  clients fire it — Radicale never sends notifications itself.
- The two htpasswd entries are the only way in; `/.well-known/caldav` is served
  by Radicale itself (302 to `/`), which is what GNOME Calendar and phones
  follow. The public host sees constant scanner traffic (all 401) — that is
  normal for a public subdomain.
